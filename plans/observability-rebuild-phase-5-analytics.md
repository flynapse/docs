### D3 — Operator binding rule (ruling 9)
`decide_binding`: if `spec.requires.operator_scoped` is false → `BindingDecision(owner_wide=False, scope_note=None)` (tenant-class relations are whole-tenant for any bound caller). If true and `auth_context["is_tenant_owner"]` → `owner_wide=True`, `scope_note = "Counts cover every operator of your organisation."`; the repository re-binds `db_tenancy(tenant_id, tenant_operator_ids(tenant_id))` for the query only. Otherwise (capability holder) → `owner_wide=False`, `scope_note = "Counts cover only the operators you are entitled to."` and the request's own binding is used. `scope_note` is part of the cache key (`owner_wide`) and of the envelope.

### D3a — Permission gating (spec §7.1; both sides)
Backend: `panel_service.get_panel_data` calls `authorize_panel(auth_context, spec)` before the limiter and the cache. A tenant owner (`auth_context["is_tenant_owner"]`) passes every panel. Any other caller must hold every id in `spec.requires.capabilities`, checked with `core.authz.context.has_capability(auth_context, cap)` (any department — the same check `is_tenant_admin` makes), and `owner_only` panels refuse non-owners; failure raises `PanelForbiddenError(code="forbidden")` → 403. The endpoint-level `is_tenant_admin` gate stays as the coarse first check. Mapping, as constants in `registry.py` (one per tab so the owner can tighten a tab in one line): `USAGE_REQUIRES`, `QUALITY_REQUIRES`, `RELIABILITY_REQUIRES` = `("view_dashboard",)`; `COST_REQUIRES = ("view_dashboard",)` (the owner may tighten to `owner_only=True` per client); `DOCUMENT_HUB_REQUIRES = ("view_dashboard", "document_hub")` for the four `document_hub_*` panels; `AUTOMATIONS_REQUIRES = ("view_dashboard", "view_all_automations")` for `automation_runs_over_time`, `automation_spend_vs_budget` and `tool_usage_mix`; Improvement panels `owner_only=True` with `capabilities=()`. `register(spec)` refuses a capability id absent from `core.authz.catalog.capability_ids()` and a non-owner-only spec whose first capability is not `view_dashboard`. ### D6 — `POST /analytics/events` contract
Authenticated (any user; identity via `resolve_request_identity`, so 401/403/409 as the ingest route). Body `ProductEventBatch` (`extra="forbid"`): `events: list[ProductEventIn]` with 1 ≤ n ≤ 50 (over → 413). `ProductEventIn` (`extra="forbid"`): `event_name` (Literal allow-list), `occurred_at` (aware datetime; values more than 5 minutes in the future are clamped to now, more than 7 days in the past → 400 `stale_event`), `department` (optional; case-normalised), `document_id`, `document_kind`, `source_surface`, `page_number`, `dwell_ms`, `route` (≤ 200 chars, must start with `/`, no query string), `attributes` (dict, ≤ 20 keys). Server stamps `tenant_id`, `user_id`, `session_id` (from `request.state.session_id`, else the `X-Session-ID` header, else null). Rate limit: `FixedWindowLimiter(key_prefix="analytics:events", window 60 s, max 60)` keyed `tenant_id:user_id` → 429 `rate_limited`. Write: `postgres.execute_many` under the request binding (one row per event). ### D7 — Ingest evolution (ruling 3, spec §3.4)
