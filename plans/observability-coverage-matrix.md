## 3. The counting rule (stated so the next derivation is comparable, not a new opinion)

**Rule v1, unchanged from the previous version, deliberately.** The totals are cited elsewhere and must stay comparable.

- **One row = one boundary.** A boundary that exists in N instances instrumented identically (the 8 parser CLIs, the 3 core sweeps) is **one row carrying an N/M count**, not N rows.
- **Three columns: span / metric / trace-correlated log.**
- **Fully covered** = all three yes. **Partly covered** = one or two. **Uninstrumented** = none of the three.
- **An inherited span counts.** If a boundary executes inside a parent span (a gateway SERVER span, `automation.run`, `automation.queue.process`), its span column is yes — the boundary is in a trace. A **metric** must be attributable to the boundary itself; a parent's metric does not cover a child.
- **Rows marked `n/a` throughout are excluded from the counts**: the `X-Trace-Id` header row, the request-identity attribute row, the two telemetry bootstrap/shutdown mechanism rows, the `traceparent`-propagation and exporter rows, the §F repo-level summary rows, and every "none of these exist in this repo" row.
- **A row with one `n/a` column cannot be fully covered.** This is why §G (dashboard) scores 0 fully covered and always will: browser boundaries have no trace-correlated-log column — they *are* the trace. **That is a property of the rule, not of the tree.** §G's prose says what actually changed.

**Three axes added this derivation. None of them changes the arithmetic.**

- **Span kind: `D` = domain span** (says what was done to what — `weaviate.bm25_search` carrying `db.system`/`db.operation`/`tenant.id`) vs **`F` = HTTP-fallback span** (says only `POST https://…`, with no `rpc.*`, no `db.*`, no bucket/key/table/model identity). *This is the single most useful distinction this document carries*: counting by the three columns says covered; counting by "can an operator tell which dependency this was" says not.
- **Method counts on every external-client row: `n/m` = methods carrying a domain span / methods present.** This is the granularity the previous version lacked, and it is what surfaces a client at 0/18.
- **A metric DERIVED at the collector** from a span or log this boundary emits is written **`yes (derived)`**. It counts as yes — the series exists — and the marker says the application itself emits no instrument.

**Why 138 boundaries and not 131.** +5 rows in §B (two builtin sweep tasks, the AD dispatcher's two entry paths, core's three automation-store sweeps as one row), +1 in §G (the app-boot / long-running settle events, which the previous version had no row for and which now carry 5 derived metrics), +1 for the new §I. **No row was deleted.**

## 4. Mechanism this audit relies on (read before judging the third column)

**Bootstrap.** `flynapse_otel.bootstrap.bootstrap()` configures the three SDK providers from `OTEL_*` env and applies the client instrumentors the *caller declares*. `utils.observability.bootstrap` (`utils-obsm/utils/observability/bootstrap.py`) is a thin wrapper that bakes in six names for every api-side process: `psycopg2, httpx, requests, urllib3, redis, threading`. Deliberately **not** declared: `botocore` (would double the `gen_ai.*` families) and `fastapi`/`asgi` (the gateway wires its own mount-aware ASGI middleware).

**Log correlation — the test the third column is judged against.** `utils.observability.log_bridge.install()` installs two loguru sinks (a JSON stdout sink and an OTLP `LoggingHandler` sink), both of which read `trace.get_current_span().get_span_context()` **at emit time** and write `trace_id`/`span_id` only when that context is valid. `utils.observability.intercept.install()` routes stdlib `logging` into loguru so non-loguru subsystems reach the same two sinks. Both are installed by `utils.logging_config.setup_logging()`, which is also what calls `bootstrap()`.

**Therefore a log line is trace-correlated if and only if both hold:** (a) `setup_logging()` ran in that process, and (b) the line is emitted while a recording span is current. A process that called only `bootstrap()` reaches loguru's *default stderr sink*, not the OTLP pipeline, and carries no `trace_id`. A line emitted outside any span carries no `trace_id` even with the sinks installed. Applied literally throughout: where a row says "yes" it means a live span encloses the log site, not merely that a log call exists.

**Auto-instrumentor consequences** (read from `/home/aditya/Code/api/.venv/lib/python3.11/site-packages`, `opentelemetry-*` 1.44.0 / 0.65b0 — **carried from the 08:52 derivation and re-confirmed only for `redis`**; see §8 item 15):

**The botocore nuance.** No `botocore` instrumentor is declared anywhere in the estate, but `botocore.httpsession` calls `conn.urlopen(...)` on a `urllib3.HTTPConnectionPool`, and the urllib3 instrumentor patches exactly that. **So every boto3 call — S3, Bedrock, SES, Cognito, DynamoDB — does get a CLIENT span and an `http.client.request.duration` sample, as an HTTP call.** What it does *not* get is AWS semantics. Rows below mark that `F`.

**The Weaviate nuance.** `weaviate-client` uses `httpx` for REST (auto-instrumented) but **gRPC** for the search path. No gRPC instrumentor is declared anywhere, so the three search modes have **no auto span and no auto metric** — which is why they now carry hand-written domain spans and still show `metric? no`, while the REST-backed CRUD operations show `metric? yes`.

### NEW — the process-wide semconv latch, and why an HTTP-coverage claim must name its generation

`OTEL_SEMCONV_STABILITY_OPT_IN` is a **process-wide latch**: `_OpenTelemetrySemanticConventionStability._initialize()` reads it once, the first instrumentor to call it fixes the mode for the whole process, and every later read is a no-op. `flynapse-otel` now both defaults it **and forces the latch** at `flynapse-otel/flynapse_otel/bootstrap.py:187-188` (`os.environ.setdefault(..., "http")` followed by `_initialize()`) — a repair landed at HEAD `f6bd5c0`. **Before that repair the mode was decided by whichever instrumentor ran first.**

The consequence was measured rather than guessed, and is recorded in `api-obsm/tests/conftest.py:47-64`: run the OTel lane alone and bootstrap wins the race, the mode is `http`, and gateway spans carry `http.request.method`, `http.response.status_code` and `error.type`; run the whole suite and an earlier lane latches `DEFAULT` first, those attributes are never written, and **six gateway tests fail with a bare `KeyError`** on the attribute they read — a failure that says nothing about the thing it is actually reporting.

> **What this means for this document:** every §A row saying "HTTP coverage: yes" describes the **new (`http`) semconv generation**, which is what a process that reaches `flynapse_otel.bootstrap()` before instrumenting anything now gets. A deployed process that instruments something *before* `bootstrap()` runs emits **old-semconv** HTTP attributes, silently, and every dashboard and alert built on the new names reads nothing. **Nothing in the deployed configuration asserts that ordering** — `conftest.py:63-64` says so in as many words. This is §8 item 2.
